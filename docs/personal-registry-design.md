# 个人 Docker 镜像仓库方案

日期：2026-11-12。项目名为 `light`。本文保留设计背景；用户已授权实施，实际实现与收敛见 [实施状态](implementation-status.md)。

## 1. 目标与结论

建设一个适合个人服务器的 Docker 镜像仓库，支持私有仓库与公开仓库：标准 Docker 命令即可登录、推送、拉取；通过中文网页查看镜像、管理机器人令牌、删除镜像和回收空间。

推荐采用 **Go 单进程 + 内嵌 React 控制台 + CNCF Distribution 协议内核 + 本地文件存储**。一个容器、一个持久化目录即可运行，不使用 PostgreSQL、MySQL、SQLite、Redis 等数据库或缓存服务。

默认只有一个管理员，新仓库默认私有，管理员可按仓库切换为公开；公开仓库允许匿名拉取。CI 和自动化使用机器人令牌，首版不设计令牌的仓库范围、路径范围或只读/读写权限选项，所有有效机器人令牌统一可以推拉全部仓库。支持 `personal/app` 等多级仓库名称，但不引入组织、项目成员、多租户或复杂角色系统。

首版面向单台 Linux 主机和本地 ext4/XFS 文件系统。不支持多副本写入、共享存储集群和高可用。文件存储消除了数据库运维，但仍需处理一致性、磁盘容量和备份。

工具链初步对齐 Go 1.26、Node.js 24、npm 11。具体依赖版本在实现前结合 Distribution 的稳定发行版确认并锁定，不直接追踪其 main 分支。

## 3. 协议内核选型

推荐将 `github.com/distribution/distribution/v3` 的 Registry HTTP 处理器和 filesystem 存储能力嵌入 Go 程序，并在其外建立生命周期、鉴权、管理和维护适配层。官方源码提供 `handlers.NewApp` 入口，但它属于项目内部耦合较强的集成点，不能假定长期稳定；应封装依赖、固定版本，并建立升级回归测试。[处理器源码](https://github.com/distribution/distribution/blob/main/registry/handlers/app.go)、[文件系统驱动](https://distribution.github.io/distribution/storage-drivers/filesystem/)。

选择该路线的原因是复用已有上传、摘要校验、manifest 和存储逻辑，降低自行实现协议的维护成本。独立 Registry 容器虽然集成简单，但与单程序目标不符；完整自研 Registry 则会显著扩大首版工作量。

先做最小技术验证：内嵌处理器、文件存储、自定义访问控制、停止后台任务、离线 GC，以及多架构 push/pull。验证通过后再建设完整控制台。如果发现依赖必须深度 fork 才能满足生命周期或安全控制，应先修订此选型，不在实现中暗中增加第二个服务。

协议目标为 Docker Registry HTTP API V2，覆盖 Docker Schema 2、OCI image manifest 和 image index。多架构镜像作为首版必验能力。OCI 1.1 Referrers、Buildx provenance/SBOM 与签名制品需针对选定版本验证，不预先宣称完整 OCI 1.1 兼容。[OCI Distribution 规范](https://specs.opencontainers.org/distribution-spec/)。

## 4. 总体架构

```text
Docker / Buildx / CI                    浏览器
        │                                │
        └──────── HTTPS 域名 ─────────────┘
                         │
                v2way 或其他 HTTPS 入口
                         │
                   light 单进程
          ┌──────────────┼───────────────┐
          │              │               │
       /v2/*         /auth/token      /api/* 与网页
     Registry 内核    令牌签发        管理 API / React
          │              │               │
          └──────────────┼───────────────┘
                         │
              Registry 文件 + JSON/JSONL
```

应用固定监听 `:5080`，Compose 固定映射宿主 `127.0.0.1:5080`；数据目录在代码中默认为 `/var/lib/light`，无需 Compose command 参数。

| 路由 | 用途 | 认证方式 |
| --- | --- | --- |
| `/v2/`、`/v2/*` | Docker/OCI 镜像协议 | Bearer token 与仓库动作授权 |
| `/auth/token` | Docker 获取短期协议令牌 | 机器人凭据换取推拉令牌；匿名仅换取公开仓库 pull 令牌 |
| `/api/*`（公开 API 除外） | 管理 API | 管理员会话、写操作 CSRF 校验 |
| `/api/public/*` | 公开仓库列表、标签和镜像详情 | 匿名只读，每次按当前可见性过滤 |
| `/` 及页面路径 | 中文控制台与公开仓库浏览 | 管理功能需登录；公开内容可匿名浏览 |
| `/healthz`、`/readyz` | 存活与就绪检查 | 仅最小状态，不返回敏感信息 |

Registry 和 API 路径必须先于 SPA 回退匹配；未知协议/API 路由不得返回网页。浏览器会话与 Docker 凭据分开验证。

## 5. 功能范围

### 首版功能

- 管理员初始化、登录、退出、修改密码；首次设置通过本机 CLI 输入，不生成内置固定密码。
- Docker 登录、push/pull、上传状态查询及恢复；多级名称、标签列表、digest 与多架构详情。
- 仓库列表、搜索、说明、镜像平台、配置与层信息、复制 pull/tag/push 命令。
- 机器人令牌：名称、生成登录用户名、到期时间、启用/停用、撤销、最近使用时间；秘密仅创建时显示一次。首版没有权限范围配置，统一推拉全部仓库。
- 仓库公开/私有切换；公开仓库支持免登录拉取及网页只读浏览，推送仍须机器人认证。
- 按单个 tag 删除镜像，预览并回收无引用内容；控制台发起 GC 预览和执行，保留离线排障入口。
- 磁盘使用与剩余空间、操作审计、维护任务状态、基础设置。

仓库在首次成功写入镜像后自动发现，不要求先在网页建项目。网页上传 tar 包不进入首版，统一通过 Docker/OCI 客户端上传。

### 后续功能

单标签解绑、保留策略、定时维护、S3、镜像同步与代理缓存、完整制品与签名展示。机器人令牌的权限范围暂不设计；漏洞扫描、在线镜像构建、镜像内容解包浏览、多租户及集群部署暂不规划。

## 6. 无数据库存储设计

```text
data/
  instance.lock
  storage.json                 # 数据格式版本
  config.json                  # 限制及基础设置
  account.json                 # 管理员与密码摘要
  robots.json                  # 机器人 ID、名称、秘密摘要、状态、有效期
  repositories/<id>.json       # 仓库名称、说明、公开/私有状态及可见性修订
  keys/                        # 协议令牌签名私钥
  registry/                    # Registry 内核独占维护的数据树
  cache/catalog.json           # 可重建的仓库摘要索引
  jobs/maintenance.json         # 在线维护状态、有限历史和预览计划
  logs/audit-YYYY-MM.jsonl
```

`registry/` 的真实目录结构由所选内核版本决定，不自行设计第二套 blob/tag 链接。应用通过内核接口操作镜像数据，不从管理 API 直接拼接路径或修改内核文件。

存储分三类：

1. **镜像事实数据**：blob、manifest、index、tag 与上传状态，以 Registry 存储为准。
2. **管理事实数据**：配置、账户、机器人凭据、仓库说明及可见性，以相应 JSON 为准。仓库管理文件使用应用生成的 ID，文件内保存规范仓库名，避免将用户路径直接作为文件路径。首次 push 可能早于管理元信息建立，缺少可见性记录时一律按私有处理。
3. **派生数据**：列表索引、大小摘要和统计，允许删除后重建，绝不能作为删除依据或授权来源。

每个管理 JSON 带 `schemaVersion`、`revision` 和更新时间；通过同目录临时文件、文件同步、原子替换及父目录同步写入。更新采用修订检查防止覆盖。启动持有数据目录排他锁，离线命令同样获取该锁。

不把所有镜像元信息塞进一个不断膨胀的 JSON，也不在每次拉取时重写文件。审计按月追加并限额；访问日志和流量统计默认保存在有界内存。令牌最后使用时间按间隔合并写入，允许异常退出丢失最近的统计。

Registry 与管理文件不建立跨文件事务：push 成功后触发索引失效和异步刷新；启动及定期扫描修正漏记事件，扫描使用分页与限并发。运行期间变化则安排补扫，页面显示更新时间和刷新中状态。删除、授权及维护预览必须查询事实数据，不能使用可能滞后的索引。

JSON 损坏时按重要性处理：账户、凭据或核心配置损坏则拒绝就绪；索引损坏则重建；审计只可修剪最后一条不完整尾行。目录同步失败导致提交结果不明时冻结相关管理写入，要求重新同步确认或重启核对，不自动覆盖。Registry 自身的断电持久化保证需单独验证，不能用管理 JSON 的原子写入保证代替。

## 7. 登录与授权

网页管理员密码采用 Argon2id 摘要，使用 HttpOnly、Secure、SameSite Cookie；会话仅存内存且有容量与期限，重启后重新登录。管理写请求校验来源与 CSRF，登录失败限速。Secure Cookie 根据当前请求协议生成；同源校验比较 Origin/Referer 与当前请求地址，不配置固定外部地址。

### 机器人令牌

管理员创建机器人令牌时，系统生成稳定 ID、登录用户名（例如 `robot-ci-<id>`）和高熵随机秘密；名称可由管理员填写。使用机器人用户名和秘密执行 `docker login`，推荐通过 `--password-stdin` 传入秘密。服务端只保存秘密摘要，秘密仅创建成功时显示一次，不能重新查看。

首版所有有效机器人令牌能力一致：推送和拉取全部公开、私有仓库，允许首次 push 自动建立仓库。界面不出现仓库选择、路径前缀、只读/读写或角色选项；`robots.json` 不引入这些权限字段。保留到期、停用和撤销等生命周期管理，审计记录机器人 ID 与名称。

机器人仅用于镜像协议访问，不登录管理控制台、不调用管理 API。删除镜像、切换仓库可见性、管理令牌和维护操作统一由管理员完成；这是身份类型的固定能力边界，不提供逐令牌权限配置。

认证流程：访问 `/v2/` → 接收 Bearer challenge → 向 `/auth/token` 交换短期令牌 → 携带令牌访问 Registry。有效机器人按客户端请求的仓库签发 pull/push scope，匿名请求仅允许公开仓库的 pull scope；明确校验 issuer、audience、签名与有效期。协议 scope 仍是标准交互必需信息，不代表引入可配置的机器人权限范围；无仓库 scope 的登录探测不附带全库权限。[官方令牌认证规范](https://distribution.github.io/distribution/spec/auth/token/)。

协议令牌建议有效期 5 分钟。访问控制适配层还检查凭据 ID 的当前状态，实现撤销后阻止后续请求；已经开始传输的请求不保证立即中止。支持客户端为长上传续取令牌，签名密钥持久化，轮换须保留明确的过渡策略。

跨仓库 blob mount 同时校验源 pull 与目标 push，匿名身份不能写入或挂载到目标仓库。首版拒绝客户端直接删除镜像和已存储的 blob，由控制台受控删除流程执行；允许机器人取消未完成的上传。Registry 原始全库 catalog 不对匿名开放，公开列表通过专用 API 提供。

### 公开仓库

可见性按完整仓库名称设置，只有“私有”和“公开”两种，不隐式继承名称前缀。新仓库默认私有；公开后匿名可读取其标签、manifest、index 与该仓库关联的 blob，不能写入、删除或读取管理信息。即使某 blob 被其他公开仓库共享，也不能借此访问私有仓库的路径。

匿名客户端可沿用标准 Bearer challenge 获取公开仓库 pull 令牌，不需要 `docker login`。若请求携带错误或失效的机器人凭据，应明确报认证失败，不静默降级为匿名。匿名网页只显示公开仓库名称、说明、标签、平台和拉取命令；机器人信息、审计、容量及系统设置不公开。

可见性保存在事实 JSON 中，不依赖 catalog 缓存授权。公开改为私有后，每个后续匿名协议请求都重新校验当前可见性，拒绝旧匿名令牌继续读取；公开 API 同样实时过滤。相关响应默认使用 `Cache-Control: no-store`，前置代理不得对其做共享缓存；已开始的传输及已被他人下载的内容无法追回。切换操作使用修订校验并写入审计。

## 8. 镜像写入、删除与回收

### 上传与读取

大镜像采用流式读写，不将层读入整块内存。协议适配层保留内核对摘要、上传偏移、Range、Accept、Location 和错误响应的处理。管理 JSON 的小正文限制和短超时不应用到 Registry 上传下载。

反向代理保留认证头、方法、查询参数、协议响应头及流式传输，不把 Registry 挂在路径前缀下。不配置外部 URL 或域名白名单；认证 realm 根据当前请求 Host 与协议生成，上传 Location 使用相对路径，页面复制命令取自浏览器当前地址。代理须保留 Host 并覆盖 X-Forwarded-Proto，不使用 X-Forwarded-Host。

初始限额建议：并发上传 4、全局上传请求大小可配置、上传空闲超时独立设置；不把全站请求总超时硬设为 60 秒。磁盘剩余低于预留阈值时拒绝新上传，实际 ENOSPC 仍需正常处理，不能假定预检消除竞争。失败上传不能发布完整 manifest；废弃上传通过内核清理接口按年龄回收，避免误删活跃会话。

### 删除语义

必须区分标签、manifest、index 和 blob。多个标签可能指向同一 digest，一个多架构 index 又引用多个平台 manifest。

删除以单个 tag 为单位，不删除同摘要的其它 tag。预览携带短期操作 ID、仓库名称、tag、当前摘要与全局引用状态指纹；执行前暂停镜像请求并获取独占锁，重新扫描，变化则要求重新预览。

回收候选仅包含所选镜像与递归索引子清单，以及这些清单的配置和 layer。同仓库其它标签、候选之外的存续清单（包括 index 和原始 subject 引用）保护其整个引用图；跨仓库存续清单及已建立的 layer 链接保护共享物理文件。清单无剩余引用、layer 无剩余引用且不在上传保护期内时通过内核接口删除，不清理无关孤立数据。只删除子清单的 tag 时，如果父 index 仍引用它，则保留清单和层。

先解绑所选 tag，再移除无引用清单和层。清理失败时如实返回“标签已删除，部分存储清理失败”，刷新列表并保留可稍后维护回收的内容。默认允许推送同名标签覆盖；覆盖产生的旧无标签内容仍沿用保留策略。

### 空间回收

删除引用与实际释放磁盘空间是两件事。Distribution 的 GC 需要阻止并发上传，否则存在误删风险；其官方文档明确要求只读或停止服务。[官方 GC 说明](https://distribution.github.io/distribution/about/garbage-collection/)。

采用**同进程维护任务**：控制台发起预览，展示清理范围后确认执行；维护期间关闭镜像请求准入、等待在途请求结束并持有独占 Gate，控制台与健康检查保持可用。任务结束后恢复镜像访问，无需停止容器、访问 Docker socket 或创建第二个服务。离线命令保留为排障入口，执行时仍须先停止实例。

网页按钮通过异步任务预览和确认回收，不默认启用 `delete-untagged`。针对多架构子 manifest 和制品依赖构造保留测试；选定版本不能安全覆盖的依赖类型，应保留相关内容并禁用对应回收路径。GC 日志记录任务状态，异常中止标记待检查，不能自动报告成功。

界面分别显示逻辑镜像大小、去重后实际磁盘占用及预估可回收量，说明共享层会导致删除释放量小于镜像大小。拉取次数按 manifest 请求估算，不宣传为精确的完整下载次数。

| 公开仓库浏览 | 匿名查看公开仓库、搜索、标签与详情，复制免登录拉取命令 |
| 存储维护 | 索引重建、GC 与上传清理的预览/执行/进度、历史记录 |
| 操作审计 | 登录、令牌变更、镜像删除、维护任务与错误 |
| 系统设置 | 当前页面访问地址、容量限制、账号安全、版本与运行状态 |

- 左栏上方为 light 品牌与“镜像仓库”副标题，中部为运行概览、镜像仓库、机器人令牌、存储维护、操作审计、系统设置；底部显示实例状态、管理员与退出入口。
- 右侧顶栏放面包屑、刷新和当前页面必要操作；主体采用页面标题/说明/操作区，再接统计卡片、筛选条及业务列表。底部状态栏展示连接状态与版本等简要信息。
- 延续 v2way 的卡片边框、紧凑间距、表单、按钮、状态徽标、复制控件、空状态、加载反馈和弹窗布局；仓库详情在同一框架内展开，避免为每类页面另起布局。
- 1100px 以下收紧侧栏与间距；720px 以下移除窗口外边距和圆角，侧栏改为带遮罩的抽屉，顶栏显示菜单入口，统计与表单按窄屏重排。长名称和 digest 提供截断、展开与复制，操作控件不得挤出视口。

## 10. 部署、备份与恢复

推荐单容器以非 root 用户运行，挂载 `./data:/var/lib/light`；不挂载 Docker socket，不需要特权和 host 网络。镜像构建采用前端、Go、运行时三阶段，前端产物内嵌，运行时包含 CA 证书。

HTTPS 优先复用 v2way：将镜像域名根路径代理到 light，确保长上传与下载使用合适的流式配置。若 v2way 使用 host 网络，可访问 light 的宿主回环映射；其他容器拓扑按实际网络连接，不把容器内 `127.0.0.1` 当作另一个容器。后续如有独立部署需求，再增加应用直接加载 TLS 证书。

生产 Docker 客户端使用受信任的 HTTPS 证书；自签证书需要部署端建立信任。管理页可与 Registry 同域，不要求第二个域名，管理 API 仍独立鉴权。

备份默认先正常停机，再复制完整数据目录，包括镜像、管理文件和签名密钥；普通配置导出不能代替备份。在线备份只在有全目录一致快照机制并完成验证后提供。恢复到新的独占数据目录，核对权限、数据版本及配置，重建派生索引，再用已知 digest 拉取验证。

升级前保留程序/容器 digest 和完整备份。数据格式升级采用显式版本与可重入迁移，拒绝较旧程序读取不兼容数据；回退必须结合备份，不承诺只替换程序即可回退。

## 12. 实施顺序与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| P0 技术验证 | 内嵌内核、文件驱动、鉴权和离线 GC 验证 | 固定稳定版本；确认无额外服务、数据库或后台生命周期泄漏 |
| P1 可用仓库 | 程序入口、管理账户、机器人令牌、公开/私有授权、HTTPS 代理说明 | 机器人全库推拉、公开仓库匿名拉取、私有仓库拒绝匿名；重启后按 digest 拉取一致 |
| P2 中文管理 | v2way 主体框架与样式、仓库列表与详情、机器人管理、公开浏览、派生索引 | 桌面/移动布局一致，身份隔离、可见性切换、索引重建、分页和命令复制可用 |
| P3 数据维护 | 删除预览、离线 GC、审计、备份恢复 | 共享层与 index 不损坏；中断可诊断；备份恢复后能拉取 |
| P4 发布交付 | Docker/Compose、CI 与用户文档 | 非 root 运行、干净环境启动与升级恢复流程验收 |

关键验收场景：

- 原生 Docker login/push/pull、Buildx 多架构与默认 provenance 行为；分别明确支持的附属制品能力。
- 大层流式传输、断线恢复、重启后恢复能力及失败重传边界；digest 校验失败不暴露半成品。
- 所有有效机器人均能推拉全部仓库；无权限范围表单；过期、停用、撤销后拒绝后续请求；机器人不能调用管理 API。
- 公开仓库匿名拉取与只读网页浏览；匿名不能访问私有仓库、推送或获取全库目录；失效机器人凭据不降级。
- 公开转私有后旧匿名令牌失效、列表和详情不泄漏、共享 blob 的仓库路径鉴权；跨仓库 mount、客户端 DELETE 拒绝、管理 CSRF。
- 页面框架、色彩、间距、卡片/表单/弹窗参考 v2way；桌面、窄屏和移动抽屉导航、长 digest、键盘焦点可用。
- 同 digest 多标签、同层多仓库、多架构父子引用，删除和 GC 后剩余镜像均可拉取。
- 进程异常退出、磁盘满、原子替换结果不明、JSON 损坏、重复任务、多进程锁和索引丢失。
- 经过真实 HTTPS 代理的上传 Location、认证 realm、Range 和长传输；非 root 权限和完整备份恢复。

开发验证优先使用临时目录、临时凭据与模拟故障；实际 Docker 集成测试、环境启动及镜像构建须在后续明确授权的实施阶段进行。本轮已安装项目开发依赖并执行自动测试；不启动开发服务、不执行构建、不创建提交。

本方案默认采用：单管理员、新仓库默认私有且可公开、统一全库推拉的机器人令牌、本地磁盘、同域控制台、外部 HTTPS、容器内维护任务及离线排障入口；页面主体框架、布局与样式参考 v2way。用户已授权实施，P0 已通过处理器集成测试；后续验收边界见实施状态文档。

2026-11-12 安全修复补充：暂停单个 HTTP 请求不足以覆盖完整 Docker 推送，采用持久化的 24 小时 blob 租约和新内容保护窗口；公开查询先筛选分页并限制并发；代理来源 IP 仅在显式配置私有 Header 后使用，缺失或无效回退 RemoteAddr。实现与验证详见 [安全修复记录](security-fixes-2026-11-12.md)。
