结论：发现 5 项需要处理的问题，其中 1 项高风险、4 项中风险。应用逻辑中的 4 项问题均在临时数据中复现；另有当前 Go 工具链的已知漏洞风险。没有修改业务代码、重启开发服务、执行 Docker 构建，或删除/修改现有开发镜像。本次检查不代表完整渗透测试或安全保证。

本轮覆盖 `internal/server`、`internal/registry`、`internal/store`、`internal/jsonfile`、`internal/maintenance`、前端 API/展示/复制代码、CLI、Docker/Compose 与依赖锁定文件。

## 1. 高：修改密码期间，旧密码登录可能获得新版本有效会话

位置：`internal/server/server.go:250`、`internal/server/server.go:256`、`internal/store/store.go:206`。

`Authenticate` 读取账户快照后执行 Argon2 校验，返回值只有布尔值；登录处理器随后重新读取最新账户 revision 来创建会话。两次读取之间没有绑定同一个账户版本。

触发顺序：

1. 旧密码登录开始，读取旧密码摘要和 revision。
2. 管理员更换密码，新密码摘要和新 revision 持久化。
3. 第一步的旧密码校验完成，登录处理器取到新的 revision，创建了不会被版本校验拒绝的会话。

影响：掌握旧密码且在密码轮换窗口内发起登录的客户端，可以获得修改密码之后仍有效的管理员会话，绕过“修改密码使旧凭据失效”的预期。攻击者仍需知道旧密码并命中并发窗口；这不是无密码登录。

验证：临时账户中，在旧密码校验进行时通过同一个 Store.Change 提交准备好的新账户摘要及 revision=2，旧密码登录仍返回 200，所得 Cookie 调用管理员机器人列表也返回 200；竞态检查模式下复现成功。新账户仅属于临时 fixture，未更改真实管理员。

建议：认证返回“实际用于校验的账户版本”，会话必须绑定该版本；版本变化时拒绝本次认证或让生成的旧版本会话立即失效，不能再次读取最新 revision 给旧密码升级授权。

## 2. 中：当前 Go 工具链存在可达的已知标准库漏洞

位置：`go.mod:3`、`web/embed.go:37`；Registry 内核的 blob 下载也调用 `http.ServeContent`。

实际执行测试、开发后端使用的 Go 版本为 `go1.26.5`，模块只要求 `go 1.26.0`。官方扫描器报告 22 个去重后的符号级候选公告，其中 20 个属于标准库，2 个属于间接依赖。候选数量不等于实际可利用漏洞数量，扫描器对接口动态分派可能保守地报告未启用的路径。

已确认存在实际暴露调用路径的是 GO-2026-6609 / CVE-2026-78667：Go 官方公告说明，包含大量小范围的 Range 头会导致 FileServer、ServeContent、ServeFile 消耗过量 CPU，修复版本为 Go 1.26.9。静态前端资源允许匿名访问，且本项目直接使用 FileServer。请求头 32 KiB 限制可以约束单次输入大小，但不替代该修复。本次没有向运行环境发送资源耗尽载荷。[官方公告](https://pkg.go.dev/vuln/GO-2026-6609)

其余标准库候选包括 HTTP/2、TLS、模板和 MaxBytesReader 相关公告。当前应用以明文 HTTP 监听，未启用原生 HTTP/2；没有把所有 HTTP/2 公告都判定为当前可利用。MaxBytesReader 公告要求请求体读取与响应头写入并发，本轮也未证实该前提在现有处理器中成立。

建议：由部署环境维护者升级编译工具链并重新发布；按本次扫描的修复版本集合，Go 1.26 分支至少应覆盖到 1.26.11。构建时校验实际 `go version`，避免仅靠 `go.mod` 的主次版本或缓存的 Docker 基础镜像判断安全补丁状态。本次没有安装或替换系统 Go，也没有构建发布镜像。

额外依赖候选：

- `github.com/klauspost/compress v1.18.4`：GO-2026-6865，修复版本 v1.20.2。公告针对 zstd 解码器 panic；镜像层目前是透明存储，扫描器给出的 Reader 接口路径不足以证明客户端上传的层会进入解码器，当前远程利用路径未证实。[上游公告](https://github.com/klauspost/compress/security/advisories/GHSA-fpmh-frq8-7rj8)
- `go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc v1.42.0`：GO-2026-6505，修复版本 v1.45.0，涉及端点 URL 写入日志。需核查实际启用 exporter 时是否在端点 URL 携带敏感信息；本轮未证实发生泄漏。[上游公告](https://github.com/open-telemetry/opentelemetry-go/security/advisories/GHSA-8wmf-6v46-5gfg)

这两个候选建议在依赖更新时一并处理，完整扫描摘要见结果 JSON。

## 3. 中：删除和 GC 没有完整保护上传与发布之间的中间状态

位置：`internal/registry/tag_delete.go:72`、`internal/registry/tag_delete.go:142`、`internal/registry/tag_delete.go:316`、`internal/registry/maintenance.go:100`。

暂停 HTTP 请求并等待 Gate 排空，只能保证没有正在执行的请求；Docker 推送包含多个请求，已经完成 layer 上传、尚未提交 manifest 的事务仍可能存在。

删除路径只从 Namespace.Repositories 获取仓库。上游目录枚举以 `_manifests` 为仓库标识，所以仅上传了 blob、还没有任何 manifest 的新仓库不在扫描结果中；代码中保护其他仓库 layer 链接的分支也不会扫描到它。

GC 则按已发布 manifest 标记引用，不会自动保留新上传但尚未发布的完整 blob。

验证：

- A 仓库已发布镜像；B 新仓库上传同一 layer，HEAD 为 200，但暂不发布 manifest。管理员删除 A 的唯一 tag 后，B 的 layer HEAD 变为 404。
- 新仓库完成一个 blob 上传，尚未发送 manifest；执行 GC 后该 blob HEAD 从 200 变为 404。

影响：正常推送与管理员删除/维护交错时，已上传内容可能被回收，造成后续 manifest 发布失败或需要重传。这次复现针对尚未发布的内容，没有证实会绕过引用保护删除其它正常存续镜像。

建议：保护完整上传事务，而不只保护单个请求。可建立有界、可恢复的暂存 blob 租约/待发布记录，并在 tag 删除及 GC 中统一纳入保护；删除扫描需覆盖尚未出现 `_manifests` 的仓库。另一保守方案是对新 blob 延迟回收，并明确定义最大支持推送时长。仅扩大 Gate 范围到扫描和删除仍不足以消除这个问题。

## 4. 中：反向代理部署时，匿名客户端可耗尽所有客户端共用的认证限流桶

位置：`internal/server/server.go:70`、`internal/server/server.go:151`、`internal/server/server.go:167`。

限流只使用 TCP RemoteAddr 和路径，忽略经过可信代理转发后的客户端身份。正常的 v2way/Vite 反向代理会让多个真实客户端共享同一个后端来源 IP。

验证：临时服务中，当前来源 IP 已有一次 fixture 登录，再发送 11 次错误登录就用完每分钟 12 次额度；随后同一来源下的正确管理员登录返回 429。`/auth/token` 使用相同模式，120 次/分钟额度也由共用代理 IP 下的客户端共享。

影响：一个匿名客户端可以持续阻断同代理后的管理员登录、机器人令牌交换和匿名公开拉取。这不会绕过认证，但会影响所有客户端的可用性；此前已签发且未过期的令牌不受令牌交换限流直接影响。

建议：在受控代理信任模型下识别真实客户端，并结合身份和全局预算分层限流；不能直接信任任意来源的 X-Forwarded-For。或者在边缘代理按真实连接来源执行细粒度限流，后端保留合理的全局安全预算。配置应兼顾直接访问与代理访问。

## 5. 中：匿名详情查询在过滤和分页前扫描全部镜像内容

位置：`internal/server/server.go:468`、`internal/server/server.go:482`、`internal/registry/registry.go:383`。

公开仓库详情先调用 Images，读取所有 tag、所有不同摘要对应的 manifest、配置及递归引用，算完大小和创建时间以后才做搜索过滤和每页 20 条的分页。公开 API 没有类似认证接口的请求频率限制，也没有独立计算并发预算。单镜像的 100000 对象上限不能限制“许多镜像 × 许多匿名请求”的总消耗。

验证：用 25 个不同摘要的临时标签构造公开仓库，匿名请求筛选后只返回 1 条数据，仍发生了 75 次 blob 正文流读取。这里测的是过量扫描事实，没有对真实服务进行压力或 OOM 测试。

影响：公开仓库规模增大后，匿名客户端可以通过重复请求放大磁盘 I/O、CPU 和内存占用，持有 Registry 读锁也会增加维护等待时间。

建议：先依据 tag 名称/摘要索引筛选和分页，只为当前页加载大小与创建时间；加入有界缓存失效机制、计算并发限制和匿名请求预算。公开性授权仍须查询事实管理数据，不能因缓存优化放宽授权。
